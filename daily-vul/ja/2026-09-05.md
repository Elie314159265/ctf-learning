## 1. CVE-2026-85046 — Google Chrome / Chromium V8 型混同(実悪用中のゼロデイ)

**原理・根本原因:** ChromeのJavaScript/WebAssemblyエンジンであるV8における型混同(タイプコンフュージョン)の欠陥です(CWE-843)。コンパイラの最適化過程で、本来`PACKED_ELEMENTS`を保持する配列に誤って`PACKED_SMI_ELEMENTS`マップが割り当てられることがあり、エンジン内部で管理している「配列が保持するデータ種別」の認識が誤った状態になります。悪意あるWebページはこの不整合を引き起こし、JavaScriptヒープ上での任意の読み書きプリミティブへと発展させることで、レンダラーのサンドボックス内でコード実行を達成できます。

**対応(緩和策):**
- Chromeをバージョン152.0.7977.82/.83(Windows/macOS)または152.0.7977.82(Linux)以降へ更新する。ブラウザ再起動時に自動更新されるが、適用状況を確認すること。
- Chromiumベースの他ブラウザ(Edge、Brave、Operaなど)も、各ベンダーが対応するパッチを提供次第更新する。

**対象:** 152.0.7977.82より前のGoogle Chrome。2026-08-04に外部の研究者が報告し、2026-09-03にパッチが提供された。Googleは実際に悪用が行われていることを確認しており、2026年にパッチが適用された6件目の実悪用ゼロデイとなる。2026-09-04にCISA KEVカタログへ追加。

## 2. CVE-2026-85596 — Traefik Kubernetes Ingress クライアント証明書認証バイパス

**原理・根本原因:** Traefik の Kubernetes Ingress プロバイダが、nginx形式のIngressアノテーション(`nginx.ingress.kubernetes.io/auth-tls-verify-client`)を内部のTLSオプションへ変換する際、生成されるオプション名はIngressオブジェクトの名前空間と名前に基づいて決まります。2つのIngressリソースが同じホスト、同じクライアントCAシークレット、同じクライアント認証モードを共有している場合、Traefikはそのホストに対するTLSオプション定義が競合していると判断し、暗黙的にエントリポイントのデフォルトTLS設定へフォールバックしてしまいます。このデフォルト設定はクライアント証明書を全く要求しないため、本来相互TLS(mTLS)を必須とするはずのルートが、誰でもアクセス可能になってしまいます。

**対応(緩和策):**
- Traefik 3.7.11以降へアップグレードする。
- パッチ適用までの間、クライアント証明書要件が複数回設定されているホストがないかKubernetes Ingressオブジェクトを監査し、クライアント証明書の要求が実際に機能しているか(例:クライアント証明書なしでの接続テストなど)を確認する。

**対象:** Traefik v3.7.0〜v3.7.10(3.7系のみ)。2026-09-04に公開開示。既知の悪用報告は現時点でなし。

## 3. CVE-2026-11613 — Divi Ajax Filter(WordPressプラグイン) 未認証ローカルファイルインクルージョン/RCE

**原理・根本原因:** 本プラグインのAJAXハンドラは`custom_loop_template`パラメータを受け付け、`loop_templates`オプションが`custom-template`に設定されている場合、そのユーザー入力値を許可リストによる検証や制限なしに、そのままPHPのファイルインクルード処理に使用します(CWE-98)。インクルード対象が攻撃者によって制御可能であり、かつ認証前に到達可能であるため、サーバー上に攻撃者のコンテンツを配置できる何らかの手段(ログファイル、アップロードされたメディアなど)と組み合わせることで、リモートコード実行につながる可能性があります。

**対応(緩和策):**
- 修正版が提供され次第、Divi Ajax Filterプラグインを5.1.2より新しいバージョンへ更新する。修正版が未提供の場合はプラグインを無効化する。
- アップロード・ログディレクトリへの直接書き込みアクセスを制限し、Webサーバーログ内の`custom_loop_template`パラメータに異常な値がないか監視する。

**対象:** Divi Ajax Filter(Divi Engine)5.1.2以前。2026-09-03に公開開示。本レポート作成時点で実悪用の確認報告はないが、未認証・ネットワーク到達可能・スキャンによる発見が容易な欠陥であり、高リスクとして扱うべき。

## 4. CVE-2026-85216 — MISP LDAP/LinOTP認証バイパス

**原理・根本原因:** MISPが独自に実装した`LdapAuthenticate`および`LinOTPAuthenticate`コンポーネントは、CakePHP標準の`FormAuthenticate`ロジックを置き換えるものですが、その入力検証チェックを再現していませんでした。その結果、空文字や文字列以外の認証情報が背後の認証処理まで到達してしまいます。LDAP経路では、有効なユーザー識別子を知っている攻撃者が空のパスワードを送信でき、「未認証バインド」を許可する設定のLDAPサーバーでは、有効な識別名(DN)と空パスワードの組み合わせに対してバインド成功を返す場合があり、実際のパスワードを知らなくてもセッションが確立されてしまいます。

**対応(緩和策):**
- 認証識別子・パスワードに対して厳密な型チェック・空値でないことのチェックを強制するMISPのパッチを適用する。
- 多層防御として、MISP認証に使用するLDAPサーバー側で未認証・匿名バインドを無効化する。

**対象:** LDAPまたはLinOTP認証を使用するMISP脅威インテリジェンスプラットフォームの、バージョン2.5.45までの導入環境。2026-09-03/2026-09-04公開。

## 5. CVE-2026-4644 — Google Cloud Integration Connectors HTTP Connectorにおける認可欠如

**原理・根本原因:** Google CloudのIntegration Connectorsサービス内のHTTP Connectorは、呼び出し元が特定のサービスアカウントを接続にアタッチする権限を持つかどうかを検証していませんでした。認証済みユーザーがこれを悪用すると、本来アクセス権を持たないより高い権限のサービスアカウントをアタッチでき、権限昇格や、より広範なGoogle Cloudプロジェクトの乗っ取りにつながる可能性があります。

**対応(緩和策):** 顧客側の対応は不要。Googleは公開開示前の2025-12-11にサーバー側で既に修正済みです。CVEレコードが今週(2026-09-04)になって公開されたため、参考情報として本レポートに含めています。念のため確認したい場合は、修正日以前に異常なサービスアカウントのアタッチ操作がないか監査ログを確認してください。

**対象:** 2025-12-11のサーバー側修正より前のGoogle Cloud Integration Connectors HTTP Connector。CVSS 8.5(High)。顧客対応は不要。

## 6. CVE-2026-82538 — ILIAS リポジトリのごみ箱テーブルにおけるSQLインジェクション

**原理・根本原因:** ILIASのリポジトリ「ごみ箱」ビューは、HTTPリクエストからテーブルのソートパラメータを受け取り、実際にソート可能なカラムの一覧に対して検証することなく、そのままSQLクエリの`ORDER BY`句に直接組み込みます(CWE-89)。データベース層でマルチステートメント実行が有効になっているため、任意のコンテナに対する書き込み権限を持つ認証済みユーザーはこれを利用してスタック型のSQLクエリを注入でき、データベースへの完全な読み書きアクセスや管理者アカウントの乗っ取りにつながる経路が生まれます。

**対応(緩和策):**
- ILIAS 9.22、10.10、11.3、またはそれ以降へアップグレードする。
- 直ちにアップグレードできない場合は、リポジトリコンテナへの書き込み権限を付与するユーザーを制限し、アプリケーションユーザーからの異常なマルチステートメントクエリがないかデータベースログを監視する。

**対象:** 9.22 / 10.10 / 11.3より前のバージョンのILIAS eラーニングプラットフォーム。2026-09-04公開。既知の実悪用報告は現時点でないが、必要な権限が低く(1つのコンテナへの書き込み権限を持つ低権限の認証済みアカウントのみ)、攻撃の敷居は低い。

## 7. CVE-2026-52767 — YesWiki 未認証ActivityPub署名検証バイパス

**原理・根本原因:** YesWikiの`HttpSignatureService::verifySignature()`は、PHPの`openssl_verify()`の結果を緩やかな論理否定(`if (!openssl_verify(...))`)でチェックしています。`openssl_verify()`は`1`(有効)、`0`(無効)、`-1`(エラー)のいずれかを返しますが、PHPの真偽判定のルールでは`-1`は「真」として扱われます。そのため、この否定処理は本来「エラー」(鍵やアルゴリズムの組み合わせが不正な場合など)であるはずの状態を、署名検証が成功した場合と同様に扱ってしまい、未認証のままリクエストを通過させてしまいます。

**対応(緩和策):**
- 戻り値を緩やかな否定ではなく厳密に(`=== 1`)チェックするバージョン4.6.6以降へYesWikiをアップグレードする。
- 関連するSSRFの問題(CVE-2026-52769、ActivityPubの`Signature.keyId`取得に関するもの)も同じアップデートで修正されているため、両方のパッチを併せて適用する。

**対象:** YesWikiバージョン4.6.2以上4.6.6未満。

## 8. CVE-2026-84642 — Mozilla Thunderbird 添付ファイルホスト名フィルタのバイパス

**原理・根本原因:** `mail.allowed_attachment_hostnames`という詳細設定は、Thunderbirdがリモート添付ファイルの取得を許可するホストを判定するための正規表現を構築するために使用されます。設定されたホスト名の値は、正規表現の特殊文字(`.`など)をエスケープせずにその正規表現へ組み込まれていたため、特定の1ドメインのみを許可する意図で設定したホスト名が、意図しない別のホスト名にも一致してしまう場合があり、添付ファイルの取得元制限が弱められていました。

**対応(緩和策):** Thunderbird 155またはThunderbird ESR 153.2へ更新する(2026-09-03付レポートで取り上げたFirefox 155 / ESR 153.2アップデートと同じリリースラインです)。

**対象:** 155より前のThunderbirdバージョン/153.2より前のESRバージョン。2026-09-01リリース。既知の実悪用はなし。
