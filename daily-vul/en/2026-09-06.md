## 1. "StyleSmuggler" — Magento Open Source / Adobe Commerce Unauthenticated Zero-Day RCE (No CVE Yet, No Patch)

**Principle / root cause:** Researchers at Sansec identified an unauthenticated remote-code-execution chain, dubbed "StyleSmuggler," that abuses Magento/Adobe Commerce's own internal classes. A crafted directive smuggled into store data (e.g., an order or customer field) is later processed when Magento renders its standard "Payment Transaction Failed Reminder" email template internally — this happens automatically as part of normal order-processing, so no one needs to open or receive the email. That rendering path ends up invoking classes that were only ever intended to run through the command-line dependency-injection compiler, allowing attacker-controlled content (including a poisoned log file) to be executed as code. No authentication of any kind is required to trigger the chain.

**Mitigation:**
- No official patch, advisory, or CVE identifier had been published by Adobe as of 2026-09-06.
- Sansec and other researchers recommend emergency virtual-patching/WAF rules blocking the known trigger pattern, closely monitoring for unexpected outbound connections and unrecognized admin/file-system changes, and increased log review around order and email-queue processing.
- Store operators should treat all public-facing Magento/Adobe Commerce installations as at-risk regardless of patch level, since the flaw affects even fully up-to-date 2.4.9 installs.

**Affected:** Magento Open Source and Adobe Commerce, all currently shipping versions including 2.4.7, 2.4.8, and 2.4.9 (reproduced by Sansec on clean installs of each). Disclosed 2026-09-05; live attacks confirmed starting 2026-09-04, with at least one fully patched store already breached.

## 2. CVE-2026-85046 — Google Chrome V8 Type Confusion Zero-Day

**Principle / root cause:** A type-confusion bug in V8, Chrome's JavaScript/WebAssembly engine, causes an array holding `PACKED_ELEMENTS` to incorrectly receive the `PACKED_SMI_ELEMENTS` map. This mismatch between the array's declared and actual internal representation lets script-level code read and write memory locations on the JavaScript heap that should be inaccessible to it, enabling code execution inside the browser's renderer sandbox when a victim simply loads a malicious web page.

**Mitigation:**
- Update Chrome to 152.0.7977.82/.83 (Windows/macOS) or 152.0.7977.82 (Linux), or later; Chromium-based browsers (Edge, Brave, Opera, etc.) should apply their equivalent updates as they become available.

**Affected:** Google Chrome versions prior to 152.0.7977.82/.83. Reported by an external researcher on 2026-08-04; patched 2026-09-03; confirmed under active exploitation in the wild (the sixth Chrome zero-day patched in 2026); added to CISA KEV on 2026-09-04.

## 3. themoos core-moos — Multiple Pre-Authentication Vulnerabilities (MOOS Robotics/Autonomy Middleware)

**Principle / root cause:** core-moos (MOOS — Mission Oriented Operating Suite) is inter-process communication middleware widely used in robotics and autonomous-vehicle research. Four related flaws were disclosed together:
- **CVE-2026-85440 (9.8):** A pre-authentication heap overflow in `MOOSCommPkt` packet handling — a negative declared packet length bypasses a signed-integer size check, causing a 4-byte heap buffer to be overflowed with attacker-controlled data during the handshake phase, before any authentication occurs.
- **CVE-2026-85428 (9.3):** The optional MOOSDB HTTP server accepts variable-write requests without authentication, letting a remote client set arbitrary MOOS variables — including ones that drive actuators or override commands in a live system.
- **CVE-2026-85455 (8.8):** A buffer over-read in packet deserialization triggered by an undersized (4-byte) packet.
- **CVE-2026-85450 (8.7):** The MOOSDB HTTP server does not bound the number of concurrent connections or in-flight header data, allowing resource exhaustion (denial of service) via many slow/incomplete connections.

**Mitigation:**
- Upgrade core-moos beyond the affected releases (all versions through 10.4.0 are affected) once a fixed release is available; track the upstream repository for the patched version.
- Do not expose MOOSDB or its optional HTTP interface directly to untrusted networks; restrict access to trusted internal hosts only, and treat any MOOS-based control system for physical actuators as safety-critical when assessing exposure.

**Affected:** themoos core-moos, all versions through 10.4.0. Disclosed 2026-09-03/2026-09-04. No known in-the-wild exploitation at time of writing, but the pre-authentication nature and potential physical-safety impact (actuator control) warrant prompt attention for any internet- or shared-network-exposed deployment.

## 4. AI Infrastructure Campaign — RAGFlow, LiteLLM and Kestra Targeted to Steal LLM Provider Keys

**Principle / root cause:** Security researchers report an active campaign systematically scanning for exposed AI-pipeline infrastructure (RAGFlow, LiteLLM, Kestra) and chaining known vulnerabilities to gain code execution, then specifically harvesting upstream LLM provider API keys and related credentials rather than just deploying commodity malware. In RAGFlow specifically:
- **CVE-2026-45312 / CVE-2026-28797:** Authenticated Server-Side Template Injection (SSTI) — RAGFlow's prompt-generator and Agent-workflow features process user-supplied content through Jinja2 templates without sandboxing, so a registered user can craft a workflow (e.g., chaining a search tool with an LLM component) that causes the server to execute arbitrary OS commands.
- **CVE-2026-24770:** A "Zip Slip" path-traversal flaw in RAGFlow's MinerU document parser lets an uploaded archive write files outside the intended extraction directory, enabling arbitrary file overwrite and subsequent code execution.

Once inside, attackers install a persistence hook in RAGFlow's LLM-credential-configuration flow (`TenantLLM`) that silently intercepts and exfiltrates provider type, model name, endpoint, and API key data every time an administrator configures or updates an LLM integration — capturing credentials configured even after the hook is planted. The broader campaign also establishes SSH persistence via injected `authorized_keys` and deploys cryptocurrency-mining malware, terminating competing miner processes on compromised hosts.

**Mitigation:**
- RAGFlow: no official patched release for CVE-2026-45312/CVE-2026-28797/CVE-2026-24770 has been confirmed as of this writing; disable or tightly restrict registration/agent-workflow features on internet-facing instances, and avoid exposing RAGFlow directly to the internet.
- Rotate all LLM provider API keys that may have been configured on an exposed RAGFlow, LiteLLM, or Kestra instance, and audit for unauthorized SSH keys and unexpected mining processes.
- For LiteLLM and Kestra, apply the fixes already listed under items 9 and 8 below (this campaign is exploiting the same underlying CVEs reported by CISA on 2026-09-02).

**Affected:** RAGFlow versions 0.23.1/0.24.0 and earlier (component-dependent); LiteLLM and Kestra deployments not yet updated per items 9 and 8. Campaign activity reported this week (week of 2026-09-01); underlying RAGFlow CVEs disclosed earlier in 2026 but exploitation newly reported as active.

## 5. CVE-2026-84754 — WPFunnels WordPress Plugin Broken Access Control

**Principle / root cause:** Several routes in WPFunnels that handle sensitive operations — such as creating orders, modifying customer data, accessing payment configuration, or manipulating funnel steps — are missing proper authentication/authorization checks in their controller logic. An unauthenticated attacker can invoke these backend endpoints directly (bypassing the normal UI) to perform actions that should require a logged-in, authorized user.

**Mitigation:**
- Update WPFunnels to version 3.12.14 or later.

**Affected:** WPFunnels WordPress plugin, versions up to and including 3.12.13. Published 2026-09-03; no confirmed in-the-wild exploitation reported yet.
